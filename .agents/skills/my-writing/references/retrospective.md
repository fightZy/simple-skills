# 写作复盘流程

通过当前对话中的写作反馈，提炼能提高文章质量、贴合用户表达习惯的规则。复盘交付的是可供用户判断的建议；用户确认具体建议后，才进入保存阶段。若同时要求成稿与复盘，先完成成稿，再给复盘建议。

## 1. 从反馈中提取证据

阅读当前可见的对话历史，对照写作要求、原稿、历次改稿、用户评价和用户自行修改的版本。围绕内容取舍、组织方式、详略、措辞、语气、排版及修改习惯，提取有证据的偏好，无需逐项凑齐。

- 用户明确表达的长期偏好，可作为直接证据；单次场景要求保留其适用条件。
- 多次一致的修改可支持候选规律，仍需区分观察与推断。用户未评价、继续下一步或仅接受某篇成稿，不等于认可其中所有写法。
- 助手自行生成的表述只是候选写法；只有用户的反馈能支持“用户偏好”这一判断。

每条观察附用户原话或改前、改后的关键片段，并说明对应哪次请求或修改。只引用实际可见内容；历史缺失时说明证据范围。没有足够证据形成新增建议时，直接说明，不为复盘编造偏好。

## 2. 提炼可迁移的规则

读取现有 `SKILL.md` 和 `references/examples.md`，将观察与已有规则、案例对照。优先补清已有规则的条件、合并重复内容；已有规则足以覆盖的问题，可以只建议补充案例或改进本次执行。

规则写成“在什么情境下，采用什么写法，达到什么阅读效果”，用能指导下一次写作的动作表达。保留体裁、读者和用途边界，将本次专有名词、业务事实与临时篇幅要求留在本次任务中。一次明确的长期要求可以提出规则；仅凭一次局部改动，宜提出范围较窄的候选建议。

用当前改稿和另一种适用情境检视建议：是否保留事实与限定、是否改善阅读、是否会误伤其他体裁。用于检视的构造例子须标注为构造，不作为用户反馈证据。新旧偏好冲突时，说明差异并建议收窄、替换或删除原规则，由用户选择。

完成条件：每条建议都有可追溯的证据、明确的适用范围，并说明相对现有 skill 增加或修正了什么。

## 3. 提交具体建议，等待确认

按建议编号呈现以下内容，可用简短段落或表格：

- **观察与依据**：用户偏好或写作特点、对应反馈，以及仍属推断的部分。
- **拟修改内容**：可直接写入的规则文本、目标文件及新增、替换、合并或删除的位置。
- **适用范围与收益**：在哪类文本中使用，解决什么质量问题；有冲突时一并指出。
- **可选案例**：展示拟保存的最小示例及必要说明，供用户决定是否一同保留。反馈依据在本次对话中说明。

请用户确认全部或指定编号，也可只批准规则或案例。复盘请求本身不授权保存推断出的偏好；确认前不修改任何持久文件。用户已明确批准当前列出的具体内容时直接执行，无需重复询问；部分批准只保存获批部分。若用户要求调整建议，先展示调整后的内容，待其确认后保存。

## 4. 保存规则与案例

通用规则融入 `SKILL.md` 对应的写作偏好段落，场景边界与规则放在一起；案例存入 `references/examples.md`。保持规则只有一个权威位置，案例用于解释尺度与边界，不再完整复述规则。

案例按写作问题组织，只保留理解差异所必需的内容：

- **情境**：仅在片段本身不足以说明用途或约束时补充。
- **原文 / 改写**：需要改善的片段与更合适的片段；只有单侧材料时不强凑成对。
- **简短说明**：解释关键差异，保留会影响应用的边界。

`examples.md` 不保存来源链接、反馈引用、对话摘要、确认日期或过程记录，也不按案例来源或确认状态分组。示例仅用于展示写法，不作为推断用户偏好的证据。

原文与改写只比较特定情境中的效果，不把案例当成固定模板。保存前去掉无关身份信息和业务细节，将拟保存的脱敏版本纳入确认。优先合并同类案例；只在新案例体现新边界或不同取舍时追加。删改既有规则或案例也纳入建议和确认范围。

## 5. 核对并交付

回读修改后的文件，核对每处变更均在确认范围内，规则无重复或未解决的冲突，案例精简且保留必要条件，引用可达。用获批案例检查规则是否能解释相应取舍，同时保留其他体裁所需的表达空间。

简要告知已保存的规则与案例、所在文件，以及仍未获批的建议（如有）。文件核对和情境推演只能验证规则是否清楚一致；后续写作中的实际效果，留待新的用户反馈继续复盘。
